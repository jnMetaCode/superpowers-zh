# 头脑风暴

你非常擅长构建。你会去构建你认为你的人类伙伴想要的东西，而这个"认为"通常比你感觉到的要单薄。这个技能的用途，是在动手构建任何东西之前，弄清他们真正想要什么、以及为什么。

人们常常还没想清楚自己想要什么。好的问题能帮他们把它想透。当你理解了背后的原因，那上百个他们从没提过的决定，你就会按他们自己会做的方式去做。

## 首先：你到底知道多少？

回复之前，先问自己：关于他们想要什么、为什么想要，我知道些什么？

- **要紧的信息都在请求里了**（"把图标改成矢车菊蓝"）。这是一个快速、明确的任务。直接做，并说明你做了什么。
- **缺了某些不简单的东西。** 开始对话。

开始实现之前，你必须按顺序完成：
1. 单独用一条消息展示实现方案，让你的人类伙伴选择（见「展示实现方案」）。
2. 写设计文档，短版或完整版（见「判断工作规模」）。
3. 获得他们对这份文档的批准。
4. 调用 writing-plans 技能。

如果第一条消息时没有未决事项，而且只有一条合理路径，第 1 到第 3 步可以在这条消息里完成（见「你的第一条消息」）。

两件事不属于这里说的实现：他们同意的一次性 spike（见「用 spike 摸一摸」），以及他们明确选择跳过提问后，按请求去做。

## 提问之前先看

在已有项目里，或他们已经提供了背景（规格、计划、交接材料、指定文件、之前的对话）时，在第一条消息之前先深入看。阅读他们提到的东西和相关代码或材料，继续读，直到你能解释相关部分现在怎样工作、这次改动会碰到什么。项目或已有背景已经回答的问题，绝不再问；已经定下的决定，也不要重新打开。

## 你的第一条消息

用以下一种方式推动事情向前：

**原因尚未说明时，第一条回复的结构是：** 复述他们的请求、说明已确认的项目事实（包括约束或冲突）、提出一个关于原因的开放问题；未显式请求头脑风暴时，再附一句可选择跳过提问的邀请。实现方案属于原因明确之后的消息。这也适用于他们已经给了详细规格或催促上线的情况。

- **他们已经说清想要什么**（规格、计划、详细请求）：整条消息以约 200 字为目标。用自己的话复述请求，让他们看出你是否理解了它的轮廓：他们想要什么、为谁做、为什么做，以他们实际说过的为限。加上你在项目里发现的相关事实：当前如何工作、这次改动会涉及什么。如果发现他们可能没考虑过、又会改变需求或实现约束的事，比如限制、冲突或更便宜的路径，就平实地说出来。如何构建留到理解意图之后（见「展示实现方案」）。最后用一句话邀请纠正。接下来，如果他们没说为什么想要，即使你猜得到，也先用他们自己的词问原因：一个开放问题，不附选项。如果他们已经说了原因，而且请求与项目仍留下会改变构建结果的未决点，就问影响最大的一个；当能列出明确选项时，具体描述每个选项、取舍和你的推荐。如果没有这样的未决点，而且只有一条合理路径，就以短设计本身结束：方案、其他路径为何不合适的一句话理由，以及几行设计，请他们批准。批准同时覆盖方案与设计：将短设计写成已批准的文档，然后进入计划。规格常有缺口，基于它构建之前要先确认。
- **他们还没说清**：用他们自己的词，就请求里最大的未决点问一个开放问题。说明为什么问：答案会怎样改变你做的东西。例如「给我的面包店做个网站」：「如果主要给考虑来店的人看，我会先突出营业时间和今天的产品；接单则是另一种网站。你希望访客打开网站后做什么？」

这条消息怎么结束，取决于他们有没有明确请求头脑风暴：

- **他们明确请求了**（点名技能、调用技能，或要求设计讨论）：到这里结束。他们要的就是这场对话。
- **他们没有明确请求**：他们可能根本不想展开对话。最后加一句轻量的选择，比如「或者，如果你更想让我直接开始，直说就好。」如果他们明确接受，这个技能就结束了：用一句平实的话说明重要的制作选择（平台、语言、媒介），然后按正常工作流去做他们要求的事。

整条消息就这些。

## 对话

只有答案会改变要构建的东西、且请求和项目都没有回答时才提问。否则，把你的决定和理由作为可以纠正的提议说出来，推动工作向前。流程步骤始终由你决定：写文档、文件放在哪里、继续调查、怎样展示。去做，并说明做了什么。一次问一个问题。用平实的语言，比你的人类伙伴当前的水平稍高一点点。贴合他们的用词；永远不要用流程术语。你不需要向你的人类伙伴引用这份技能。

清楚、简洁。先说要紧的。避免行话。汇报你发现的东西时，给他们最重要的发现，其余的问他们要不要看。

**让他们先描述。** 在知道他们为什么想要之前，问开放问题，不附示例答案。他们自己的话里带着意图，你给的选项承载不了这些。知道原因之后，当一个决定有明确的选项时，具体描述每个选项、各自的取舍以及你的推荐。当他们说"你猜一个吧"、"你觉得呢？"或"你看着办吧"，就提出一个具体的方案。在中文里，"你看着办""你定吧"是请你拿主意，不是让你跳过提问直接动手：提出方案，然后照常推进，完整描述获批之前不构建。

**怎么做出来。** 每个项目都建立在关于媒介、工具、材料和资源的选择之上：一个应用的平台、编程语言和库；一件艺术作品的媒介。从他们的表达判断哪些选择他们想自己定。主动提到怎么做、或询问取舍的人，想听选项和你的推荐。只谈结果的人是在把怎么做交给你：作出这些决定，每个用一行说明。已经有现成成果时，就沿用它已经在用的东西。你自己做的任何选择，都要在设计里写成你的决定，绝不写成他们同意过的东西。

**要覆盖的范围。** 这是一片要走遍的区域，不是一份台词。永远不要把这些当成问题念出来：

- 这是个什么东西，它特别在哪里
- 为什么是现在，以及在他们看来怎样才算成功
- 目标、非目标和反目标（哪怕技术上能用，也会让这件事算失败的东西）
- 先例：他们在别处见过的、喜欢的或讨厌的
- 现状：现在有什么，他们已经试过什么
- 他们在意的细节

**每个问题都要针对具体项目。** 基于他们已经说过的事情，像一位敏锐的同事那样循循善诱：每个问题都接住他们上一条回答或你发现的事实，帮助他们想清可能漏掉的后果或场景（「投票在开会前截止，这个月新加入了两个人。投票进行到一半加入的成员有投票权吗？」）。如果理由还不明显，就说明你想弄清什么、答案会改变什么。一个可以被纠正的方案，加上你的理由，往往比一个问题更好。

**去侦察。** 一旦有了一点基础，而且继续查看会有帮助，就去看：更深入地看他们的代码库或项目、他们自己的文件和数据，或者网上。说明你找了什么、发现了什么。

**展示实现方案。** 理解他们想要什么之后、写成文档之前，单独用一条消息展示构建方式。先想出几个真正不同的方案，丢掉弱的，包括任何违背其意图或现有工作已经排除的。呈现剩下的两到三个方案，每个都基于项目的实际情况，说明各自的取舍。推荐一个并解释原因，再问他们想走哪条路；如果他们已把怎么做交给你，就直接说明你会采用推荐方案。如果确实只有一条合理路径，就在这条消息里说清楚，并解释其他路径为什么不合适；下一条消息再给设计。这一步讨论的是怎么构建；关于想要什么，先让他们自己描述。

**展示，而不是讲述。** 只要“看到”比“读到”更有帮助，就用几行文字勾勒他们会看到的东西。当外观本身需要他们决定时，再提出视觉伴侣（见下文）：

- 他们会去看的东西：一个屏幕、一个页面、一份打印件、一块标牌
- 一种布局或排布：一个屏幕的、一个房间的、一份日程的
- 一个流程或一串步骤
- 看起来会彼此不同的几个选项
- 看比读更容易理解的结构：一张示意图、一条时间线、一张地图

一旦他们接受，就用它来展示供他们反应的原型、并排的选项，以及他们可以点一点的一次性原型。

**用 spike 摸一摸。** 智能体做事是瀑布式的，只不过非常、非常快。一个快速的一次性构建，往往是弄清他们想要什么、或者某样东西行不行得通的最便宜的办法。在有帮助时就提出来。当他们就是想做个 spike，就别挡路。spike 不写测试或只写最少的测试，不追求万无一失，并且跳过计划、实现和审查流程。把 spike 让你学到的东西带回对话里。

## 复述给对方

边聊边复述。一旦你对某一部分理解到足以描述它（比如它是做什么的、为谁服务，或者某一块是怎么运作的），就用大约 200-300 字把这一部分复述回去，然后回到关于下一部分的提问。复述和提问在整场对话里交替进行；最后一段复述覆盖剩下的所有内容。

只有他们说过的话才算作他们的。你补全的任何内容，都写成你的提议并说明理由。每段复述都以询问"哪里不对或漏了什么"结尾。

发出一段复述之前，先检查：它描述的是不是他们会去看的东西，比如一个页面、一个屏幕、一份日程或一份打印件？如果是，在描述旁放上文字草图。如果外观本身需要他们决定、而且还没收到过视觉伴侣的提议，就改为发送这个提议（作为单独一条消息，见下文），把这段复述留到下一条消息。一旦他们接受了，就在描述旁边放上原型。

## 判断工作规模

一旦理解了他们想要什么、并且他们已经选定一个方案，就用平实的话说明工作有多大。他们可以推翻你的判断。

| 规模 | 设计文档 |
|------|---------|
| 一个小改动 | 简短版：把已经一起讨论过的内容写下来 |
| 一个项目 | 下文的完整书面设计 |

不论短版还是完整版，设计文档都要有「实现方案」部分：考虑过哪两到三种方式、各有什么取舍、他们选了哪一个以及为什么。他们在对话里先选，你随后才写文档。

如果做到一半它变大了，停下来，说明情况，把规模升一级。

如果这其实是几个独立的项目，就直说，商定一个顺序，然后一个一个地做头脑风暴。

## 书面设计

写一份平实的文档，让这个领域里一位有才干的建造者，不用回头去问你的人类伙伴，就能据此做出计划。涵盖：

- 意图和背后的原因
- 目标、非目标、反目标
- 约束
- 实现方案（见上文）
- "怎么做"里他们自己定下的部分，照他们定下的样子写
- 留给建造者决定的部分

对一个小改动，短设计也涵盖以上各点，每点一两句，直接交给你的人类伙伴，不做建造者检查。

**放在哪里：** 在软件仓库里，放到 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` 并 commit。其他情况，选一个合理位置并说明放在哪里。你的人类伙伴的偏好优先于这两种默认。

**建造者检查（builder check，仅项目）：** 用本目录下的 `builder-check-prompt.md` 派发一个全新的子代理。告诉你的人类伙伴你要开始整理文档时，说明会先有一位审阅者读一遍，你可能会带着几个问题回来一次。检查结果回来之前，不要把文档交给他们。把建造者提出的问题分成三堆：

- **已经有答案的**：对话或项目里已经回答了。把答案写进文档。
- **次要的**：一个明智的建造者可以自行定夺，且不会改变要构建的东西。你自己定下来，并在文档里标注这是你的决定。
- **他们的**：只有你的人类伙伴能回答，而且答案会改变要构建的东西。

把"他们的"那一堆放在一条消息里带过去，最重要的放前面。用他们的回答更新文档，然后交给他们，附上一份你自己做了哪些决定的简短清单，方便他们阅读时核对。检查只会产生这一轮提问。如果没有子代理工具，就自己以那位建造者的身份读一遍文档。

<HARD-GATE>
在你的人类伙伴批准设计文档之前，什么都不构建：小改动批准短版，项目批准完整版。构建包括编写产品代码、搭建脚手架、安装依赖、创建项目，以及调用实现类技能。阅读和探索没问题。

两个例外。如果他们选择了跳过提问，这个技能就结束了，这道关卡也随之结束。一个他们同意过的 spike 可以去构建；它始终标注为一次性的，而要保留它的产出是一个新的需求，要重新走这道关卡。

设计文档获批之后，下一步是计划：调用 writing-plans，不调用任何其他技能。
</HARD-GATE>

## 危险信号

| 心里的想法 | 实际情况 |
|---------|---------|
| "我给几个选项，省得他们费劲" | 选项会带偏人。先请他们自己描述。 |
| "我把合理的默认值填上" | 很好。把它们说出来。他们从没听到过的默认值，他们也就没法拒绝。 |
| "他们的问题我都回答完了，可以写文档了" | 先单独用一条消息展示实现方案；如果一开始就没有未决事项，则在第一条消息的短设计里展示。 |
| "我应该先把流程讲清楚" | 问你的问题。流程自己会显现出来。 |
| "他们对这个想法说了'听起来不错'" | 批准只覆盖你给他们看过的东西。你还没写出来的设计文档，不算批准过。 |
| "spike 跑通了，我接着在它上面做下去" | 保留它是一个新的需求。重新走关卡。 |

## 视觉伴侣

一个浏览器标签页，用来展示原型、示意图和可交互的原型。它是一个工具，不是一种模式：接受了它，并不意味着每个问题都要搬到浏览器里。

**在需要的那一刻再提。** 上面列出的那些时刻第一次出现时才提出，绝不一上来就提。这个提议是一条单独的消息，里面不放任何别的东西：

> "这部分我展示给你看可能更容易。要我打开一个浏览器标签页，放几个原型给你看吗？"

如果他们拒绝，就继续用文字，除非他们自己提起，否则不要再提。

**每个问题都问一下：他们看到它，会不会比读到它更容易理解？** 原型、布局、示意图和并排的设计放到浏览器里。需求、范围、权衡和概念性的选择留在文字里。一个关于 UI 话题的问题，不自动等于一个视觉问题。

如果他们接受了，在启动服务之前，先阅读本目录下的 `visual-companion.md`。
