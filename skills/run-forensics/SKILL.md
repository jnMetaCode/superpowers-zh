# 运行取证：从录像里读，不从记忆里编

## 概述

**核心原则：问的是已经发生的事，就先读录像，再回答。**

让 agent 解释「你刚才为什么那么做」，它是在总结自己的上下文窗口。工具返回值、shell 退出码、没人提过但确实被改动的文件——这些早就不在窗口里了。于是答案来得流畅、笃定、偶尔是错的。这比「我不知道」更糟：它会被相信，然后被写进 commit message。

本 skill 依赖 [OrcaReplay](https://github.com/Continuum-AI-Corp/OrcaReplay)（Apache-2.0，npm，Node 20+）。它在**进程外**、于模型提供方的 HTTP 边界录制运行过程，事后可以在断开提供方的情况下把录像放回去重跑。

```bash
npm i -g orcareplay
```

## 何时使用

- 上一次运行改了文件、跑了命令、或把构建搞挂了，没人知道是哪一步。
- 同事报了一个你复现不出来的失败，而你没有他的 key、也没有他的机器。
- 想把一次失败的会话变成回归测试，而不是 issue 里的一段描述。
- 有人把 agent 自己的解释当结论用，而你需要知道证据支不支持。

**不要用于**：规划下一步改动、审查 diff、调试没有 agent 跑过的代码。**没有录像就直说没有**，并提议先录一次——不要用回忆顶替。

## 对国内开发者的两个具体用处

**一、重跑一次会话是零 token 成本的。** 回放时不联系模型提供方，录下来的响应逐字节放回去。调一个 prompt 改动、验证一次失败能不能复现、给同事演示一遍——都不再按次计费。用中转/网关按量付费的人，这一条最直接。

**二、把「我到底连到了哪个端点」变成可查的事实。** 各家工具读的环境变量并不统一：有的读 `OPENAI_BASE_URL`，有的只认 `OPENAI_API_BASE`，有的在配置里钉死、环境变量完全无效。录像里记的是实际发出去的请求，所以「明明设了中转地址却还是走了官方」这类问题，不用靠猜。

## 输入

- 运行标识，或者「最近那次」。
- 具体要解释什么：某个文件改动、某条命令、某次构建失败。
- 要的是解释、复现，还是换模型对比。
- 回放可以波及多大范围：能不能碰数据库、容器、别的主机。

## 步骤

1. **先确认有录像。** 跑 `orca list`。空的就直说，并提议 `orca record <agent> -- <命令>`；到此为止，不要从记忆里重建。
2. **按问题类型只读需要的部分。**
   - *发生了什么* → `orca show <run>`：模型轮次（含 token 数与停止原因）、工具调用的参数与结果、shell 命令与退出码、改过的文件。
   - *为什么会这样* → `orca graph <run> --to <事件>`：只取到那一个事件的因果链。把 200 条时间线全读一遍再推理，更慢、更费上下文，而且正好会诱发本 skill 要防的那种笃定猜测。
   - *现在还能复现吗* → `orca replay <run>`。
3. **每条因果判断都标来源**：`recorded`（录制时看到的）还是 `inferred`（查询时按某条规则推出来的）。两者不能混着说。
   - ✅「trace 显示第 14 步的 `rm` 删掉了它。」
   - ✅「按时间推断像是第 14 步那个 `rm`——这条是 inferred，不是 recorded。」
   - ❌「第 14 步删掉了它。」（在只有 inferred 的情况下）
4. **第一次回放前，先把录下来的 shell 命令读一遍。** 回放不是 dry run：agent 进程会再跑一次，它当时发出的每条命令也会再跑一次。先列出会重复执行什么。
5. **回放到临时 worktree**（`orca replay <run> --worktree`）。否则录像里的文件树会覆盖当前工作区，未提交的改动在回放期间消失——中途打断就一直消失。
6. **逐字报出结论行**，然后说清楚还剩下哪些不确定。

## 输出

- 一句话回答被问的那个问题。
- 支撑它的具体事件：序号、类型、关键参数、退出码。
- 每条因果判断标上 `recorded` / `inferred`。
- 若做了回放：逐字引用结论行（`reused` / `exact` / `divergences` / `unmatched`），并说明哪些副作用真的重复执行了。
- 录像覆盖不到的部分。

## 边界：三句不能说的话

- **回放对上了不等于确定性结论。** 它证明的是这次录像能复现，不是模型稳定。
- **`egress=blocked` 只挡模型提供方的出网，不是网络隔离。** 回放时录下来的工具调用照样真执行——录到过 `curl` 就会再次访问网络。回放不是沙箱。
- **默认适配器不捕获 embedding 调用。** 所以 RAG 的检索那一步不在 trace 里，哪怕对话轮次是完整的。

## 常见问题

- **现象**：明明看着跑完了，`orca list` 却是空的。
  **处理**：该工具把 provider 地址钉死在自己的配置里、不读 base-URL 环境变量，所以什么都没录到。改用 `orca attach --port <n>`，把工具配置指向这个端口。
- **现象**：`reused=3/5` 看着像只成功了一半。
  **处理**：通常不是。harness 会为自己发一些请求（额度探测、会话命名），回放不重复它们。
- **现象**：视觉类 agent 回放出来是 divergences 而不是 `exact`。
  **处理**：正常。重新渲染的截图字节不同。
- **现象**：Node 项目里回放起不来。
  **处理**：临时 worktree 是按已跟踪文件建的，`node_modules` 不在里面。这类就地回放，并在报告里说明原因。
